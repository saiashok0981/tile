# Tile macOS release research

Checked 2026-10-21 against first-party Apple and GitHub documentation. This note records platform requirements and a practical release sequence; it does not assert that Tile currently meets them.

## Downloadable macOS app

- For distribution outside the Mac App Store, sign the app with a **Developer ID Application** certificate. Apple says the app should use the hardened runtime and a secure timestamp for notarization; an ad-hoc signature is not a substitute. Developer ID certificates and notarization require Apple Developer Program membership. [Apple: Developer ID](https://developer.apple.com/developer-id/), [Apple: notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple: program benefits](https://developer.apple.com/help/account/membership/programs-overview/)
- In a custom build, sign distributable code with the Developer ID identity and hardened runtime. Submit a ZIP, DMG, or PKG with `xcrun notarytool submit ... --wait`; inspect the log, even on success. Apple no longer accepts `altool` uploads. [Apple: distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/), [Apple: custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- For ZIP delivery, notarize a ZIP containing the app, staple the ticket to the **app**, then recreate the ZIP for users; a ZIP itself cannot be stapled. Validate the final downloaded container and launch it on a clean Mac if possible. [Apple: custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow), [Apple: packaging and testing](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution)
- Notarization is an automated security check, not App Store review. Gatekeeper checks the Developer ID signature and notarization ticket when a downloaded app launches. [Apple: notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple: macOS distribution](https://developer.apple.com/macos/distribution)

## GitHub Releases and website

- Create a version tag and a **draft GitHub Release**, attach the actual signed/notarized macOS ZIP as a release asset, write install instructions and release notes, then publish. GitHub's auto-generated "Source code" archives are source snapshots, not the installable app. GitHub allows up to 1,000 assets per release and each file must be under 2 GiB. [GitHub: managing releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository), [GitHub: about releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
- GitHub Pages can publish a static website from a selected branch/folder or a GitHub Actions workflow. An `index.html`, `index.md`, or `README.md` entry file must be at the publishing source root. A `docs/` directory on `main` is a simple option for this repository, but a separate `site/` build and Actions workflow is also supported. [GitHub: publishing source](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [GitHub: creating a site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)
- Host the landing page on the repository's `github.io` Pages URL first, with the Download button linking to the release **asset** on GitHub. A custom domain can be added later; GitHub Pages supports and can enforce HTTPS. [GitHub: Pages quickstart](https://docs.github.com/en/pages/quickstart), [GitHub: custom domains](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site), [GitHub: HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)

## Release order recommended for Tile

1. Freeze a version, verify the app's icon/Spotlight presentation and terminal behavior from an extracted download, and document supported macOS and architecture.
2. Obtain or confirm Developer ID access, update packaging from ad-hoc to Developer ID signing with hardened runtime, notarize, staple, and repackage the final ZIP.
3. Create the versioned GitHub Release as a draft and attach that tested ZIP. Create a simple Pages landing page with a screenshot, compatibility/install text, and a direct release-asset download link.
4. Publish the GitHub Release and Pages site after the final URL and download have been checked. Keep signing credentials outside the repository; if CI release automation is added, use GitHub's secret storage. [GitHub: Actions secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)
