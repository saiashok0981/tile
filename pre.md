# Tile agent awareness: implementation plan

Prepared 22 October 2026. This is a design and implementation plan for Tile; it does not change Tile's code.

## Scope and decisions

- First-class agent support: **Claude Code, Codex, and Gemini CLI**.
- Status integrations are **opt-in per agent in Tile Settings**. Users can inspect and disable each integration, and installation must preserve their existing configuration.
- “Current workspace” means **the active numbered workspace in the active Tile window**. The overview, attention queue, and next-attention shortcut operate within that scope. Pane badges remain visible wherever their panes appear.
- Monitor agents running in Tile-owned terminal panes first. A pane remains a terminal; Tile should take the user to the original CLI for approval or answers. Support for other terminal apps would be a separate integration and is not implied by Tile's current architecture.
- The UI must distinguish a reported state from a guess. Missing or stale data is **Unknown**, never an invented “working,” “done,” or usage figure.

## What the reference site shows

The page presents a single agent list, per-agent activity, permission and question prompts, quota bars, a completion message, and a click-to-jump action. It advertises monitoring, approval, and terminal jumping for several CLIs. These are **observations of the public page and publisher claims**, not proof that the downloadable app implements them exactly or uses any particular internal API. No Vibe Island app binary was inspected. The separate [Vibe Island docs](https://vibeisland.app/docs/) describe an overview that surfaces approvals, questions, and finished tasks. Tile should reproduce the useful workflow in its own macOS interface, not assume the reference app's mechanisms.

## Tile's starting point

Tile is a native AppKit/Swift terminal app using SwiftTerm, not Electron. `TerminalSession` owns each `LocalProcessTerminalView`, its shell PID, pane UUID, and directory (`Sources/Tile/TerminalSession.swift`). Its current `hasRunningCommand` checks foreground process groups and child processes; it cannot identify an AI agent or tell whether one is awaiting approval. `PaneView.updateActivity()` uses that generic signal for a green border (`Sources/Tile/TileWindow.swift`). `Workspace` groups panes, `TileWindow` selects a workspace/pane and renders pane headers and a toolbar, while `TileApp` owns all windows and routes keyboard shortcuts (`Sources/Tile/TileWindow.swift`, `Sources/Tile/main.swift`). `TileAction` and shortcut settings live in `Sources/Tile/Settings.swift`. `WorkspaceSnapshot` saves pane and workspace identities, but restoration starts fresh shells; a saved pane UUID is not proof that an earlier agent is still running (`Sources/Tile/WorkspaceSnapshot.swift`).

## Proposed architecture

1. Add an `AgentMonitor` owned by `TileApp`, with a provider adapter for each of the three CLIs. It receives small structured events from opt-in integrations and publishes immutable state snapshots to the UI on the main actor.
2. Give each live process a correlation key: provider + provider session ID + Tile pane UUID + launch generation. Pass a Tile-specific pane token and a local bridge endpoint through each pane's shell environment when possible; hooks echo that token back. Validate incoming events against the live pane and process generation. CWD/title alone are weak hints because several agents may run in one directory. Sessions started before integration was enabled may remain unlinked until they emit a supported event.
3. Use a private local IPC bridge (for example, a Unix domain socket with user-only permissions), bounded JSON messages, short timeouts, and a versioned schema. Hook helpers send only event type, IDs, timestamps, source, status, and optional usage by default. They return success quickly and never approve/deny, alter prompts, or block an agent when Tile is closed. Handle hook configuration as a reversible, opt-in merge; keep a backup and restore only Tile-owned entries when disabled.
4. Normalize provider events into `AgentState` (`running`, `approvalRequired`, `questionRequired`, `failed`, `completedNeedsReview`, `idle`, `unknown`) plus `source`, `observedAt`, `lastEventID`, and optional pending action. Keep terminal activity as a separate `terminalBusy` property; it is not a substitute for agent state. Age out stale signals to `unknown` and clear pending actions only on a supported resolution event, process exit, or explicit user dismissal with clear UI wording.
5. Keep a short local event ledger for deduplication and review state, with bounded retention and no prompt/response bodies by default. Never sync it. The UI reads a single derived `AttentionQueue` and overview snapshot so every badge and shortcut agrees.

### Provider signal map

| Provider | Strong signals available now | Important limits |
|---|---|---|
| Claude Code | [Hooks](https://code.claude.com/docs/en/hooks) include `SessionStart`, `PermissionRequest`, `Notification`, `PreToolUse`, `Stop`, `StopFailure`, and `SessionEnd`. `PermissionRequest` identifies a pending approval; `PreToolUse` can identify `AskUserQuestion`; `StopFailure` reports a failed turn. The [status line JSON](https://code.claude.com/docs/en/statusline) supplies session ID, estimated session cost, context data, and rate-limit windows when available. | `Notification(permission_prompt)` can follow an approval request, so it must not create another alert. `Stop` means a turn ended, not that the whole task was verified. A status-line bridge must coexist with any status line the user already configured. |
| Codex | [Codex hooks](https://developers.openai.com/docs/hooks) expose `PermissionRequest`, `PostToolUse`, `Stop`, `Interrupt`, and lifecycle events for a CLI integration. The [Codex app server](https://developers.openai.com/codex/app-server) exposes approval/question requests, turn/item lifecycle, `thread/tokenUsage/updated`, and `account/rateLimits/read`/updates for sessions managed through that interface. | CLI hooks alone may not cover every question or token metric. The app-server path needs a deliberate ownership/session-linking design and must not be assumed to observe every already-running interactive CLI. The Codex hook transcript path is not a stable API. |
| Gemini CLI | [Hooks](https://geminicli.com/docs/hooks/reference/) expose `SessionStart`, `Notification` with `ToolPermission`, `AfterTool`, `AfterAgent`, `AfterModel`, and `SessionEnd`. [Experimental terminal notifications](https://geminicli.com/docs/cli/notifications/) report action-required/completion through OSC 9 or BEL when enabled. | The permission notification observes an approval but does not grant it. `AfterAgent` is turn completion. `AfterModel` may fire for streaming chunks, so token counts need a documented aggregation rule and validation. OSC 9 support in SwiftTerm/Tile needs a targeted test before use. |

Do not parse screen text, ANSI output, or undocumented private quota endpoints to assert exact status. Generic process discovery may display “possible Claude/Codex/Gemini process” with **Unknown** state until a provider event links it to a pane.

## The nine requested features

| Feature | Tile UI and behavior | Implementation seam |
|---|---|---|
| 1. Global Agent Overview | A compact toolbar control shows live agents and actionable count in the active numbered workspace of the active Tile window; opening it shows provider, pane, state, last update, and signal source. | `AgentMonitor` snapshots filtered to that workspace; toolbar view in `TileWindow`. |
| 2. Attention Queue | Sort approval, question, failure, then completed-needs-review; show one row per unresolved action with a Jump action. Keep completed items until reviewed/dismissed or the session exits. | Reducer creates stable attention items from normalized events. |
| 3. Per-Terminal Agent Status | Pane header gets provider icon/name and short status (`Working`, `Approval`, `Question`, `Failed`, `Review`, `Unknown`), accessible text, and subdued/urgent color. Retain the current generic command border as independent terminal activity. | `PaneView` subscribes by pane UUID; avoid driving status from `hasRunningCommand`. |
| 4. Keyboard-First Navigation | Add configurable `Next agent needing attention` and `Return to previous pane` actions. Next cycles deterministically through queue items, activates the owning window/workspace/pane, and focuses the terminal. Return restores the exact prior window/workspace/pane if still present. | `TileAction`, `Settings`, `TileApp.handleShortcut`, `TileWindow.selectWorkspace`/`focusTerminal`; choose collision-free defaults when implementing. |
| 5. Usage and Quota Awareness | Show used/remaining percentage and reset time only if the provider exposes both a reliable window and timestamp; label account/plan and freshness. Show `Unavailable` when absent. | Claude status-line `rate_limits` can include 5h/7d windows and reset epochs for eligible subscriptions. Codex app-server `account/rateLimits/read` returns ChatGPT Codex windows where available. Gemini CLI `/stats` offers an interactive display, but no documented machine-readable quota feed was established for Tile; leave unavailable until one is verified. Do not confuse API rate limits with a ChatGPT/Claude subscription allowance. |
| 6. Session-Level Usage Tracking | Show sourced token counts and an **estimated** USD session cost only when the underlying data and pricing basis support it. Label the metric (`session total`, `current context`, `account total`) and provider. | Claude status line has cumulative estimated `cost.total_cost_usd`, while context-window token fields are not automatically cumulative session totals. Codex app-server thread token updates can be accumulated per linked thread with reset/replay handling; account usage is not a session metric. Gemini model usage metadata needs streaming deduplication; do not derive a cost until model, token classes, billing route, and official price are known. Subscription users should not see an estimate presented as an additional bill. |
| 7. Quiet, Adaptive Notifications | Routine start/progress/completion: pane badge and optional quiet banner. Approval/question/failure: stronger toolbar indicator and optional macOS notification; respect Do Not Disturb, foreground state, and per-event preferences. | Notification policy consumes *new* attention-item transitions; never notify on every render or poll. Clicking returns to the Tile pane. |
| 8. Reliable Agent Detection | Show precise status only from documented hook/app-server events tied to a live pane; display source and last-seen time in details. Unknown is a first-class state. | Provider adapters + correlation + staleness rules; process scan is a discovery hint only. |
| 9. Event Deduplication | One actionable notification for one pending approval/question/completion, even if two hooks describe it or an event is retried. | Prefer provider event/action ID. Otherwise fingerprint provider + session + turn + event type + stable tool/action fields within a bounded time window. Store delivered state; clear when resolved/new turn occurs. Specifically coalesce Claude `PermissionRequest` with delayed `Notification(permission_prompt)`. |

## Usage source details and display rules

- Claude Code [status-line documentation](https://code.claude.com/docs/en/statusline) explicitly lists `rate_limits.five_hour` and `seven_day` used percentages/reset timestamps, with availability limited to eligible subscription/gateway sessions and only after a first API response. Compute “remaining” as `100 - used`, label it as a percentage of that window, and preserve `resets_at` as a source timestamp. Status-line `cost.total_cost_usd` is an estimated cumulative API cost for the session. Its `context_window` numbers describe context usage, not total tokens ever spent in the session. If a status line already exists, require a safe wrapper that forwards stdin and preserves the original display output; do not overwrite it silently.
- The Codex [app-server documentation](https://developers.openai.com/codex/app-server) lists ChatGPT account rate-limit windows with `usedPercent` and `resetsAt`, per-thread token updates, and separate account-wide usage. Scope these to an authenticated managed integration. The hooks-only path can show status but must leave unavailable metrics blank when it lacks a supported source.
- Gemini CLI [hooks](https://geminicli.com/docs/hooks/reference/) expose model `usageMetadata` but streaming can emit several chunks. Track a session total only after inspecting emitted payloads for cumulative-vs-incremental semantics; otherwise show the current observed turn metric with a caveat or `Unavailable`. The CLI's [interactive `/stats` command](https://geminicli.com/docs/reference/commands/) is evidence of user-visible quota data, not an integration API.
- All quotas and costs need source, sample time, units, and unavailable/stale state. Never treat a price-card multiplication as provider-reported spend. Never read stored CLI credentials merely to display usage.

## Delivery order and acceptance checks

1. **Identity and event bridge:** Add pane launch tokens, local IPC, opt-in install/remove flows for each provider, fixtures for provider payloads, and a state reducer. Verify user hook settings survive enable/disable and a missing Tile socket never blocks the CLI.
2. **Attention and pane UI:** Add per-pane status, overview, queue, jump/return actions, and accessibility labels. Test multiple agents in one directory, panes moved between workspaces/windows, a pane closed/reopened, and Tile restarted while an agent exits.
3. **Notification policy and deduplication:** Test duplicate approval hook/notification, repeated retries, resolution, back-to-back turns, foreground/background and Do Not Disturb behavior. No duplicate macOS alerts for one action.
4. **Usage adapters:** Add Claude status-line data and quota first, then Codex app-server managed-session metrics, then Gemini metrics only after validating aggregation. Test missing fields, subscription/API modes, resets, stale values, and model changes. Never fill an unavailable metric with zero.
5. **End-to-end provider checks:** In Tile panes, trigger an approval, a question (where documented), a failing tool/turn, successful turn completion, and resume/restart for each provider. Record which states are supported and which remain Unknown. A turn completion enters review state; it must not imply tests passed or code is correct.

## Open design/verification points before coding

- Prove a robust hook-to-pane correlation method with Tile's actual shell launch API. A shell child can inherit an environment token; verify propagation and nested/multiplexed sessions before relying on it.
- Verify the current installed versions of Claude Code, Codex, and Gemini CLI against their documented hook schemas. These interfaces evolve.
- Check whether SwiftTerm exposes OSC 9/BEL notifications to Tile without corrupting terminal output; only then decide whether to use Gemini's terminal notification path as an extra signal.
- Decide whether Codex app-server sessions should be launched/owned by Tile in a later phase; hooks remain the plan for ordinary interactive Codex CLI panes. Do not promise question/usage completeness for unmanaged CLI sessions.
